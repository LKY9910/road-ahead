## 1. 교통안전 신호등 실시간 정보

정식 이름: **행정안전부 한국지역정보개발원_(전국 통합데이터) 교통안전 신호등 실시간 정보**. [공공데이터포털 및 Swagger](https://www.data.go.kr/data/15157604/openapi.do). 공공데이터포털의 해당 서비스 활용 신청과 일반 인증키가 필요하다.

| 구분 | GET 엔드포인트 |
|---|---|
| 교차로 목록·중심 좌표 | `https://apis.data.go.kr/B551982/rti/crsrd_map_info` |
| 방향별 현재 신호·잔여 시간 | `https://apis.data.go.kr/B551982/rti/tl_drct_info` |

공통 요청: `serviceKey=***` 필수, `pageNo`, `numOfRows`, `type=json` 또는 `xml`, `stdgCd`(지자체 법정동코드) 선택. 서울 `1100000000`, 인천 `2800000000`, 대구 `2700000000`, 울산 `3100000000`. 공개 명세에 교차로 ID 필터는 없다. 필요한 지역의 페이지를 받아 `(stdgCd, crsrdId)`로 클라이언트에서 합친다. `numOfRows=500`은 이번 실측에서 동작했으며 서버의 최대값으로 단정하지 않는다.

실제 JSON은 `header`와 `body`가 최상위이고 `body.items.item`이 배열이다. XML은 `ApiResponse` 루트였다. 빈 응답에는 `items` 자체가 없다.

| 쓸 필드 | 의미·주의 |
|---|---|
| `header.resultCode`, `resultMsg` | 실제 성공 `K0`, 데이터 없음 `K3`. HTTP 200만으로 성공을 판정하지 않는다. |
| `body.totalCount`, `pageNo`, `numOfRows` | 페이징·지원 범위 확인. 목록에 존재하는 교차로와 현재 신호를 제공하는 교차로는 다르다. |
| `stdgCd`, `crsrdId` | 지역을 포함한 교차로 식별자. ID만 전역 유일하다고 가정하지 않는다. |
| `crsrdNm`, `mapCtptIntLat`, `mapCtptIntLot` | 교차로 이름, 위도, 경도. 맵 API에서 받는다. 차로·진입선 형상은 제공되지 않았다. |
| `totDt` | 신호 표본에서는 `yyyyMMddHHmmss` 생산/집계 시각. 지도 목록의 오래된 시각을 신호의 나이로 쓰면 안 된다. |
| `regDt` | 울산 신호에서는 초마다 바뀌는 시각 문자열. 명세의 ‘등록일자’ 설명과 실제 사용이 다르다. |
| `{방향}{동작}SttsNm` | 현재 상태. 관측값 `stop-And-Remain`, `protected-Movement-Allowed` 등. 미지원 방향은 빈 문자열. |
| `{방향}{동작}RmndCs` | 문자열 숫자 또는 빈 문자열. 공식 설명은 센티초이나 아래 단위 불일치가 있다. |

방향 접두사: `nt` 북, `et` 동, `st` 남, `wt` 서, `ne` 북동, `se` 남동, `sw` 남서, `nw` 북서. 동작 접두사: `Stsg` 직진, `Ltsg` 좌회전, `Utsg` 유턴, `Bssg` 버스, `Bcsg` 자전거, `Pdsg` 보행.

**방향 정의의 확인 한계:** 공식 설명은 ‘교차로 신호제어기 기준 북쪽·동쪽…’까지다. 북쪽에서 교차로에 진입하는 차인지, 북쪽으로 진행하는 차인지 명시하지 않는다. 맵 응답에도 진입 차로·신호그룹 매핑이 없어 중심 좌표와 heading만으로 두 해석을 구별할 수 없다. 현장/공급기관 기준이나 별도 차로 매핑 없이 `heading → 방향`을 확정하지 않는다. 시연 후보는 데이터 수신 후보이며 진행 방향 매칭을 검증한 후보는 아니다.

**시간 단위 실측:** 울산 오지벌사거리의 `ntStsgRmndCs`가 생산시각 `16:06:47`의 `10000`에서 `16:06:48`의 `9000`으로 줄었고, `16:06:56`의 `1000` 다음 관측에서는 위상이 바뀌었다. 관측 스케일은 **1,000값/초(밀리초 상당)**로, 명세의 센티초(100값/초)와 10배 차이가 난다. `255000`이 한동안 고정되는 사례도 있어 모든 양수를 유효한 카운트다운으로 취급할 수 없다. 해당 값의 예약값 여부는 미확인이다. 서울·인천·대구는 두 번씩 조회했으나 모두 `K3`여서 지역 간 단위 비교는 불가능했다.

**주기·지연·나이:** 울산 16회 단기 조회는 약 1.14~1.20초 간격이며 생산시각 변화는 1~2초, 값은 같은 위상에서 생산시각 1초당 1,000씩 감소했다. 이 16회의 HTTP 전체 요청 시간 중앙값 **166.83ms**, 최대 **191.89ms**였다. 이어 2초 휴지 간격으로 100회 더 조회했다. 오지벌사거리·울산대학교의 직진 신호는 유효 감소 구간 110개 모두 **1,000값/초**였고, 같은 방향 위상의 재등장 간격은 각각 **161초·181초**였다(약 2초 표본 간격의 경계 검출 오차 포함). 명세대로 100으로 나누면 이 주기와 맞지 않는다. 목화예식장은 고정값·불규칙 감소가 섞여 보류 후보로 분리했다. 이는 현장 신호등과의 동기 검증이 아니다.

실시간 API 전체 정상 데이터 응답 118회의 지연은 중앙값 **149.67ms**, 최대 **323.30ms**. 연결 재사용 없이 요청 함수 시작부터 본문 수신까지 잰 값이다(초기 일부는 urllib, 이후는 curl 프로세스 실행·TLS 포함). 표본 크기도 3~500건으로 다르므로 본문의 크기가 같은 순수 네트워크 지연으로 해석하지 않는다. 생산 주기를 정확히 1초로 보장한다는 뜻은 아니다. [집계 및 위상 전환](spikes/road-ahead/api-summary.json)에는 요청 수·표본별 근거가 있다.

PC 시계가 NTP보다 **29.88초 느렸다**. HTTP `Date`도 PC보다 약 30초 앞서 신호 생산시각의 미래 현상을 설명한다. `HTTP Date - totDt`는 세 교차로의 반복 표본에서 **0~1초**였다(둘 다 초 해상도이며 서버 간 시계 오차도 포함). 원시 `PC 수신시각 - totDt`를 데이터 지연으로 보고하지 않는다. NTP 오프셋과 HTTP Date를 구분해 비교하고, 실제 신호등부터 서버까지의 지연은 현장 기준이 없어 미측정이다.

**제한·오류:** 포털의 개발계정 기본 신청 가능 트래픽은 **5,000회/일**, 운영계정 증설은 활용사례 등록 후 신청한다. 초당 수치 제한은 공개 페이지에서 확인하지 못했다. T-14 도구는 서비스별 로컬 일일 480회 상한을 두어 요청한 500회 미만을 유지했다. 1초 폴링을 하루 지속하면 86,400회이므로 기본 개발 한도로 상시 운영할 수 없다. 명세 오류는 `K01~K05`, `K10~K12`, `K20~K22`, `K30~K33`, `K90`, `K99` 계열이며 실제 무자료 코드는 `K3`처럼 0 패딩이 달랐다. 포털 GW 오류는 `20`(키 누락/권한 거부), `22`(일일 초과), `23`(초당 초과), `30`(키 미등록) 등 별도 형식일 수 있다.

**지원 범위 확인:** 맵 API를 지역별로 페이징한 뒤 실시간 API 결과와 교집합을 낸다. 이번에는 서울 지도 2,779건이 있어도 실시간 조회는 무자료였고, 전국 실시간 399건이 모두 울산이었다. 울산 지도는 402건이었다. 이것은 측정 시점의 범위이며 영구적인 서울 미지원 선언이 아니다.

## 2. 기상청 도로위험기상정보

정식 이름: **기상청_도로위험기상정보**. [공공데이터포털 15159041](https://www.data.go.kr/data/15159041/openapi.do)은 **LINK 서비스**이며 실제 제공처는 [기상청 API허브 교통안전 2.1](https://apihub.kma.go.kr/apiList.do?seqApi=971&seqApiSub=293). 공공데이터포털 일반 키와 API허브 `authKey`는 별개다. 기존 일반 키는 HTTP 401 ‘유효한 인증키가 아닙니다’였고, 사용자가 교체한 API허브 키로 ZIP 수신에 성공했다.

`GET https://apihub.kma.go.kr/api/typ04/url/road_file_down.php`

| 요청 | 의미 |
|---|---|
| `authKey=***` | API허브 인증키, 해당 API 활용신청 필요 |
| `roadNum=045` | 고속도로 노선번호, 필수. 앞자리 0 유지 |
| `tm=202610280705` | `yyyyMMddHHmm`, **UTC**. 문서상 생략하면 최신이나 이번 생략 요청은 502였다. |

12개 지원 노선: `001` 경부, `012` 무안광주대구, `015` 서해안, `020` 새만금포항, `025` 호남, `027` 순천완주, `030` 서산영덕, `035` 통영대전·중부, `045` 중부내륙, `050` 영동, `055` 중앙, `251` 호남지선. 실제 제공 여부는 노선별 요청 후 ZIP 내 좌표·링크를 확인한다. 전체 노선의 모든 위치에 관측값이 있다고 가정하지 않는다.

응답은 JSON이 아니라 ZIP(`application/x-zip-compressed`)이며 CSV가 들어 있다. 10월 표본에는 `R045_LINK_FOG_202610280705.csv`, `R045_1KM_FOG_202610280705.csv` 두 파일만 있었다. 내부 경로는 `RWS/PRODUCT/FOG/202610/28/`였다. 시즌 밖 FRG 파일이 없는 것을 정상 ‘결빙 없음’ 데이터로 만들면 안 된다. 살얼음 제공 기간은 11/15~3/15, 안개는 연중이다.

[공식 파일 포맷 정의서](https://apihub.kma.go.kr/getAttachFile.do?fileName=road_format_20251215.pdf) 기준이며 실제 FOG 헤더와 대조했다.

| CSV 필드 | 의미 |
|---|---|
| `LINK_ID` | 표준노드링크 ID. 문자열 유지 |
| `F_NODE`, `T_NODE` | LINK 파일의 시작·끝 노드 ID |
| `F_LON`, `F_LAT`, `T_LON`, `T_LAT` | 구간 양끝의 경도·위도. 격자 인덱스 변환 없이 앞길 거리/방향 판정에 사용할 좌표가 있다. 완전한 곡선 도로 형상은 별도 표준노드링크가 필요하다. |
| `S_NUM` | 1KM 파일에서 동일 링크를 나눈 구간의 순번 |
| `FOG` | 가시거리 위험 단계: 0 정보 없음, 1 관심, 2 주의, 3 위험. **관측 가시거리 m 값은 없다.** |
| `B_ICE` | FRG 파일의 살얼음 위험 단계 0~3. 이번 실제 응답에는 FRG가 없어 헤더·값 실측은 못했다. |
| `FLAG` | 1KM 파일에서 0 분석, 1 관측 |
| `X_GRID`, `Y_GRID` | 참조 격자 인덱스(정의서 범위 1~681). 경위도로 해석하지 않는다. |

가시거리 단계는 관심 `500m 이상~1,000m 미만`, 주의 `200m 이상~500m 미만`, 위험 `200m 미만`이다. CSV의 0은 ‘정보 없음’이며 ‘안개 없음’으로 확정하지 않는다(정의서의 개요 표와 필드 설명 표현이 다르므로 보수적으로 처리). 정의서 4쪽에 FOG 격자 파일명을 `5KM`로 쓴 부분이 있지만 예시·실제 파일명은 `1KM`였다.

**주기·지연:** 공식 생산·제공 주기는 **5분**. 같은 중부내륙선의 07:05/07:10 UTC 파일에서 LINK 572행·1KM 1,494행은 같았고, 주의 단계는 각각 `4→0`행·`14→0`행으로 바뀌었다. 이어 07:30 파일도 수신했다. 두 연속 자료의 생산 간격 300초와 값 변화는 검증했지만, 파일이 API에 처음 게시되는 순간이나 실제 기상 관측부터의 지연은 측정하지 못했다. ZIP 성공 3회의 전체 지연 중앙값 **265.51ms**, 최대 **328.25ms**. 실패 요청을 성공 지연에 섞지 않는다.

**오류·제한:** 실제 HTTP 401(인증키 부적합), 403(별도 도로기상관측 3.1 활용신청 필요), 502/503(HTML GW 오류)을 보존했다. 503의 원인이 요청 빈도 제한인지 일시 장애인지는 확정할 수 없다. 수 분 뒤 같은 시각 요청이 200으로 성공했다. 공개 2.1 명세에는 일일·초당 호출량의 숫자가 없어 **사용자 API허브 신청/마이페이지에서 확인 필요**다. 확인 전 시험 상한은 480회/일이며 제품의 재시도는 즉시 반복하지 않고 최소 60초 이상 간격을 둔 뒤 최신 정상 파일의 생산시각을 검사할 것을 권고한다. 이는 보장된 서버 한도가 아니라 이번 실패를 고려한 시험 권고다.

**보조 관측 API:** `GET https://apihub.kma.go.kr/api/typ01/url/road_stn_obs.php`는 별도 3.1 서비스다. `mode=2`, `var=11`(중부내륙), `tm1=yyyyMMddHHmm`(**KST**), `disp=1`, `help=1`, `authKey`로 시도했으나 403이었다. 2.1의 `roadNum=045`와 3.1의 `var=11`은 다른 코드 체계다. 이 거부는 핵심 2.1 미지원이라는 뜻이 아니다.

## 3. 국토교통부 재난상황정보

정식 이름: **국토교통부_재난상황정보**. [포털 15160258](https://www.data.go.kr/data/15160258/openapi.do) 역시 LINK이며 [ITS 제공처 명세](https://its.go.kr/opendata/opendataList?service=disaster)를 따른다. ITS 발급 키와 해당 서비스 이용 범위가 필요하다.

`GET https://openapi.its.go.kr:9443/disasterInfo`

필수 요청: `apiKey=***`, `category=D`, `eventType=all` 또는 재난 유형, `startDate`, `endDate`(`yyyyMMdd`), `getType=json` 또는 `xml`. 선택: `minX`, `maxX` 경도, `minY`, `maxY` 위도. 이번에는 `20261028` 하루를 전국 조회했다.

| 쓸 필드 | 의미·실제 형식 |
|---|---|
| `header.resultCode`, `resultMsg` | 성공은 숫자 `0`, `SUCCESS`. HTTP 상태와 본문 코드를 모두 검사 |
| `body.totalCount`, `body.items` | 건수와 이벤트 배열. 표본은 1건 |
| `eventId`, `category`, `eventType`, `eventDetailType` | 이벤트 ID, 분류 D, 유형/세부 유형. 변경·중복 제거 키로 사용 |
| `status` | 유형별 상태 코드. 표본의 산불 `2`는 진화 완료라 현재 위험으로 읽으면 안 됨 |
| `startDate`, `endDate` | 문서상 `yyyyMMddHHmmss`. 실제 endDate는 12자리여서 초 생략도 고려해야 함 |
| `locationInfoType`, `locationInfo` | 실제 JSON은 소문자로 시작. 1 점, 2 선, 3 영역; 좌표는 `경도 위도,경도 위도...` 문자열 |
| `linkId`, `roadName`, `roadNo`, `roadDrcType` | 연결 링크·도로명·도로번호·방향. 빈 문자열 가능 |
| `lanesBlockType`, `lanesBlocked` | 통제 종류와 막힌 차로. 통제 종류 0 미획득, 1 없음, 2 부분, 3 차로 부분, 4 전면, 5 우회, 6 양방향 교차 |
| `socName`, `socExtent`, `message` | 피해 시설 이름·범위·상세 설명. 도로명과 시설명은 다름 |

유형은 **D03 침수, D04 하천 범람, D06 땅꺼짐, D07 화재**다. D03 세부 1 지하차도 침수 위험, D04 세부 1 하천 홍수 경보, D06 세부 1~8 원인 유형, D07 세부 1~4 산불 단계로 정의된다. D06 상태 1 복구 중, 2 임시 복구, 3 복구 완료; D07 상태 1 진화 중, 2 진화 완료, 3 산불 외 종료다.

**설계와의 차이:** 이 서비스에서 일반 공사·교통사고 코드는 확인되지 않았다. 별도 [ITS 돌발상황정보](https://its.go.kr/opendata/opendataList?service=event)의 `https://openapi.its.go.kr:9443/eventInfo`가 필요하다. 요청 `type=all`, `eventType=cor`(공사)/`acc`(사고)/`wea`/`ete`/`dis`/`etc`/`all`, 좌표 범위, `getType`, `apiKey`; 응답의 `eventType`은 한글 이름이고 `coordX`, `coordY`, 통제 필드가 있다. 첫 요청은 **HTTP 401, resultCode 4009**, ‘인증키 신청 항목에 포함되어 있지 않음’으로 거부됐다. 사용자가 ITS 마이페이지에서 돌발상황정보를 추가 신청한 뒤 같은 키 재조회가 정상 `0/SUCCESS`로 성공했다. 원래 재난 API의 결과와 이 보조 API의 결과를 분리해 보존했다.

추가 승인 뒤 수도권 범위 `minX=126.7,maxX=127.3,minY=37.3,maxY=37.8`에서 **182건(공사 153, 교통사고 6, 기타돌발 23)**을 받았다. 정상 요청 1회의 지연은 **1,607.23ms**(중앙값·최대도 동일, 표본 1개)다. 실제 응답에는 `eventId`가 없었으며, 통제 종류는 빈 문자열이고 `lanesBlocked`·`message`에 차로 설명이 있는 항목도 있었다. 공사·사고를 위한 중복 키와 통제 해석을 재난 데이터와 완전히 같게 만들면 안 된다. 돌발 API의 갱신 주기는 이번 단일 성공 요청으로 측정하지 않았다.

**주기·지연·한도:** 30초 간격 6회, 약 150.55초 동안 동일 이벤트의 본문은 변하지 않았다. 새로운 사건/변경이 없는 이 관측으로 서버 갱신 주기를 확정할 수 없다. 표본은 13:55 발생·15:00 진화 완료 산불이며 현재 활성 위험의 위치 실측이 아니다. 재난 정상 요청 총 7회의 지연 중앙값 **109.74ms**, 최대 **137.00ms**. 열람한 [ITS 공식 이용 매뉴얼](https://its.go.kr/file/opendata/openapi_manual.pdf) 3쪽은 키별·서비스별 하루 트래픽 제한이 현재 없으며 과다 사용 시 추후 적용될 수 있다고 안내한다. 상세 서비스 페이지에는 초당 한도 수치는 없다. 시험에서는 이 안내와 관계없이 서비스별 일일 480회 상한을 유지한다.

공식 결과 메시지: `SUCCESS`, `4001` 사용량 제한, `4002` 파라미터 오류, `4004` 페이지 오류, `4005` 인증키 오류, `4009` 시스템 오류. 실제로 서비스 신청 범위 부족도 4009에 담겼으므로 숫자 하나만으로 장애 원인을 분류하지 않는다. 지원 지역은 날짜·좌표 범위로 조회하고 반환 좌표/링크를 확인한다. 빈 결과는 그 영역이 영구 미지원이라는 증거가 아니다.

## 4. 계획에 반영할 측정 한계·권고

- 신호는 교차로별로 같은 위상의 연속 응답 최소 3개에서 값 감소량/생산시각 증가량을 비교한다. 100/초·1,000/초 중 일관된 스케일이 없거나 값이 고정되면 남은 초 발화를 보류한다. 두 응답만의 우연한 차이로 단위를 확정하지 않는다. 이는 현장 신호와의 정합성을 보증하는 보정이 아니다.
- 신호 화면의 경과 시간은 수신 직후의 값과 단조 시계로 줄인다. 수신 이후 **3초** 동안 새 생산시각을 확인하지 못하면 신호 발화·카운트다운을 숨기는 시험 기준을 제안한다. 수신시각만 새로워도 오래된 본문일 수 있어 생산시각의 증가도 검사해야 한다. 최초 데이터의 절대 나이 판정에는 보정된 시계가 필요하다. 이번 3초는 측정된 약 1초 생산 간격과 0.2초 수준 요청 시간을 고려한 후보값이며 차량 검증 완료 기준이 아니다.
- 기상은 5분 자료를 경로 주변에 캐시하고, 생산시각 기준 **10분**을 넘으면 새 날씨 위험을 발화하지 않는 시험 기준을 제안한다. 이번 성공 표본은 과거 시각 명시 요청으로 받은 자료이므로 실시간 최신 게시 지연을 검증한 자료가 아니다.
- 재난은 종료·해제 상태와 빈 통제 정보를 먼저 처리한다. 공사·사고 서비스 신청을 추가하기 전에는 그 기능의 실시간 시연을 확정하지 않는다. API 오류·무자료를 ‘안전’ 값으로 바꾸지 않는다.
