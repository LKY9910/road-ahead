# T-23 주차·관광 API와 목적지 콜백 실측

2026-10-29 · Codex. **시험용이며 제품 코드는 수정하지 않았다.** API 측정 시각은 각 표본의 `requestedAtKst`이고, 에뮬레이터는 `emulator-5556`, Pleos API 34/user 10, NaviHelper 3.0.5·Navi Service 3.0.4·내비 3.3.2-rc5-hotfix.3이다. 기어·속도·GPS는 쓰지 않았고 P/0 상태에서 목적지 설정·취소만 했다. 별도 앱은 `com.roadahead.spike.parkingtravel`이다.

결론: 시설·요금·빈자리 결합과 목적지 설정 감지는 가능하다. **주차 데이터 생산시각은 없어서 ‘10분 이내 빈자리’ 조건은 구현할 근거가 없다.** 관광 행사에는 새 법정동 지역코드를 써야 한다. 목적지 상세는 자동 push에 맡기지 말고 명시적으로 조회해야 한다. 아래 권고는 Claude의 설계 결정을 위한 자료이며 DESIGN은 바꾸지 않았다.

근거: [API 명세](../APIS.md), [기계 집계](parking-travel/summary.json), [키 제거 표본](parking-travel/samples/), [콜백 타임라인](parking-travel/navi-timeline.txt). 응답 배열이 100행을 넘으면 커밋 표본에 `excerpt.receivedRows/savedRows`와 원본 해시를 표시했다. 전체 키 제거 원본은 `spikes/parking-travel/.gradle/raw/`에 보관하며 커밋하지 않는다. 배열을 잘라 놓고 전국 전체라고 표시하지 않는다.

## 1. 주차 API 세 기능 — 동작 / 신선도는 불가

[공식 포털](https://www.data.go.kr/data/15099883/openapi.do)에서 2026-10-01 기술문서를 내려받아 DOCX XML을 읽고 실제 호출과 비교했다. 최신 경로는 `Parking_v1/PrkSttusInfo_v1`, `PrkOprInfo_v1`, `PrkRealtimeInfo_v1`이다. 지시서의 `PrkSttusInfo` 그대로 호출하면 HTTP 400·XML 오류 12 `NO_OPENAPI_SERVICE_ERROR`가 온다. [오류 표본](parking-travel/samples/parking-old-operation-error.json).

| 기능 | 실제 핵심 필드 | 결과 |
|---|---|---|
| 시설 | `prk_center_id`, `prk_plce_nm`, `prk_plce_adres`, `prk_plce_entrc_la/lo`, `prk_cmprt_co` | 이름·좌표·총 구획. 이름·좌표가 빈 항목은 제외해야 함 |
| 운영 | 관리 ID, `basic_info.parking_chrge_bs_time/bs_chrge`, 일별 운영시간 | 기본시간·요금 있음. 금액이 빈 문자열인 행이 많음 |
| 실시간 | 관리 ID, `pkfc_ParkingLots_total`, `pkfc_Available_ParkingLots_total` | 총 구획·주차가능 구획 있음. **생산·갱신시각 없음** |

공통 GET 변수는 `serviceKey=***`, `pageNo`, `numOfRows`, `format=2`; 선택 변수는 `sidoCd`, `sigunguCd`다. 관리번호 단건 조회는 공식 명세에 없다. 실제 유효 관리 ID·가짜 ID를 각각 넣어도 총계 4,632와 같은 첫 10행이 돌아왔다. 미지원 인자를 오류 없이 무시하므로 ‘단건 조회 성공’으로 오인하면 안 된다. [유효 ID 인자](parking-travel/samples/parking-realtime-id-filter.json), [가짜 ID 인자](parking-travel/samples/parking-realtime-invalid-id.json).

성공 본문은 최상위 `resultCode="0"/resultMsg="SUCCESS"`다. 숫자는 문자열이다. 잘못된 지역 `99/99999`는 HTTP 200·성공 코드·빈 배열을 반환했다. 따라서 HTTP 성공, 데이터 없음, 요청 지역 오류를 구분한다. 장애·인증·한도 오류의 형식과 코드, 요청 지연은 [APIS 5절](../APIS.md#5-한국교통안전공단-주차정보--t-23)에 정리했다. 이번에는 키·한도 오류를 일부러 발생시키지 않았다.

## 2. 전국 크기와 세 지역 범위 — 부분

최초 시설 총계는 **1,737,445행**이었다. 한 페이지 10,000행·100,000행이 실제 반환됐다. 서버의 최대 허용값은 공개 명세에 없고, **100,000은 검증한 크기이지 확정 상한이 아니다**. 첫 100,000행은 HTTP 본문 **39,740,090 bytes**, 고유 ID 99,415개였다. 중복 ID가 있으므로 totalCount를 고유 주차장 수라고 부르면 안 된다.

전국 총계에 해당하는 **18페이지를 실제로 내려받았다.** 본문 합계 **683,877,454 bytes(683.88MB)**, 실제 배열 합계 **1,733,740행**, 고유 ID **1,733,155개**, 중복 **585행**이었다. 총계보다 실제 행은 3,705개, 고유 ID는 4,290개 적다. 순차 조회이며 일관된 스냅샷·완전한 전국 목록을 보장하지 않는다. 원인은 미확인이다. 페이지별 건수·전송량은 [summary.json](parking-travel/summary.json)의 `fullNationalFacility.pages`에 남겼다.

전체 수집 결과에서 이름·수치 좌표가 있고 0/0이 아닌 항목을 ID로 중복 제거하니 **305,896개**였다. `[ID, 이름, 위도 숫자, 경도 숫자]`로 직렬화한 JSON 스트림 **23,887,061 bytes**, gzip(level 6) 스트림 **7,014,971 bytes**를 계산했다. 요금·지역코드가 없는 최소 필드 크기이며 최종 앱 자산·APK 크기는 아니다. 첫 10만 행만으로 예측했던 gzip 12.6MB와 실제 수집 결과 7.0MB가 달라, 첫 페이지를 전국에 일반화하지 않았다. 대용량 원본과 별개로 커밋 응답 발췌는 합계 약 2.85MB다.

전국 실시간 목록은 **4,632행·고유 ID 4,632개**, 빈자리 양수 **1,467행**이다. 전체 행의 필드 합집합은 관리 ID와 구획 수 2개뿐이다. 시각이 있는 행 **0개**여서 ‘갱신 10분 이내 비율’은 **미상(null)**이다. 신선한 행이 0%라는 뜻이 아니다. 포털의 갱신주기 ‘실시간’과 기술문서 서비스 개요의 ‘일 1회’도 다르므로 수신시각을 갱신시각으로 대체하지 않는다.

**전국 결합 범위는 좁다.** 실시간 ID 4,632개 중 수집한 전국 시설의 ID와 정확히 매칭되는 것은 **878개(18.96%)**, 이름·유효 좌표까지 있는 것은 **487개(10.51%)**였다. 아래 중구·강남의 100% 지역 매칭률과 다르다. 나머지 3,754개를 이름·좌표가 확인된 주차장처럼 표시하면 안 된다. 관리 ID를 임의로 잘라 맞추거나 유사 이름으로 결합하지 않았다.

지연은 요청 시작부터 본문 수신까지 PC에서 측정했다. API 캐시·망 상태·전국 대용량 다운로드가 섞여 있으므로 앱의 응답 보장값이 아니다. **주차 43회·관광 28회**, 총 71회 호출했다.

| 기능 | 호출 수 | 지연 중앙값 / 최대(ms) | 표본 조건 |

강남·울산은 페이지를 나눴을 때와 100,000행 단일 요청을 모두 비교했다. 울산은 단일 요청에서도 totalCount보다 배열이 1행 작았다. 원인을 중간 갱신·중복 중 하나로 단정하지 않는다. 중구·강남 실시간 70개 ID는 각각 시설에 전부 매칭됐다. 운영→시설은 중구 3,609/3,609, 강남 17,084/17,084, 울산 10,632/10,633(99.99%)이다. 지역 표본 매칭률을 전국에 일반화하지 않는다.

## 3. 요금 — 필드는 동작, 범위는 부분

운영정보 `basic_info`에 기본시간(분)·기본요금(원)이 실제 있다. 따라서 ‘필드가 없으면’ 호출하기로 한 전국주차장정보표준데이터는 호출하지 않았다. 해당 공식 경로·필드는 [APIS 5절](../APIS.md#5-한국교통안전공단-주차정보--t-23)에 보완 후보로 기록했으며 TS의 확장 ID와 표준 데이터 ID의 실제 매칭률은 **미측정**이다.

운영 총계가 시설과 거의 같아도 유효 요금 범위는 훨씬 좁다. 중구 3,537행은 기본시간이 30인데 기본금액이 빈 문자열이었다. **시간만 있다고 요금이 있다고 판정하거나, 금액 공백을 0원·무료로 바꾸면 안 된다.** 예시 동국제강은 실제 기본시간 30·기본요금 4,200이다. `fxamt_info`의 일·월 정액 0은 기본요금이 무료라는 뜻이 아니다. 기본요금을 모르면 설계대로 요금 문장을 생략한다.

## 4. 관광 API — 동작 / 필터 사용 주의

[공식 포털](https://www.data.go.kr/data/15101578/openapi.do)의 KorService2와 실제 응답을 비교했다. 관광 API는 **28회** 호출해 50회 제한 안에 있다. 모든 좌표 요청은 소수 셋째 자리로 반올림했다.

| 표본 중심 | 3km 관광지(12) | 문화시설(14) | 레포츠(28) | 5km 위치 목록 행사(15) | 5km 종류 전체 |
|---|---:|---:|---:|---:|---:|
| 서울시청 `126.978/37.567` | 50 | 14 | 2 | 5 | 444 |
| 태화강국가정원 주변 `129.297/35.548` | 7 | 1 | 2 | 2 | 48 |

`locationBasedList2`의 `mapX/mapY/radius/contentTypeId/arrange=E`는 동작했고 거리순 `dist`를 받았다. 그러나 위치 목록의 행사에는 기간이 없다. `searchFestival2`에는 **기간과 좌표가 함께 있고 거리 필드가 없어** 앱에서 Haversine 거리를 계산해야 한다. `detailIntro2`로 기간을 얻을 수도 있으나 행사마다 추가 호출이므로 이번 설계의 최대 2회에는 맞지 않는다.

**중요한 누락 조건:** 같은 날짜에 `areaCode=1` 서울·7 울산은 0건을 반환했지만, `lDongRegnCd=11`은 서울 **19건**, 시청 5km·오늘 기간 포함 **14건**을 반환했다. 전국 오늘 행사는 69건이다. 새 행사 행들의 기존 `areacode/sigungucode`는 공백이었다. 새 법정동코드 또는 지역 인자 없는 날짜 조회를 써야 한다. 울산 `lDongRegnCd=31`은 그날 0건이었다. [서울 기존 필터](parking-travel/samples/tour-seoul-festivals-day.json), [새 필터](parking-travel/samples/tour-seoul-ldong-today.json).

`eventStartDate=eventEndDate=20251220`에 시작일 20251212·종료일 20260104 행사가 포함됐다. 날짜 창과 **기간이 겹치는** 행사가 반환되므로 시작일이 요청일 이후라고 가정하지 않는다. 도착 예정일을 두 인자에 같이 넣고 `eventstartdate <= 예정일 <= eventenddate`를 다시 검사한다. 오늘 조회 0건·오류를 서로 구별한다.

## 5. NaviHelper 목적지 콜백 — 부분

시험 앱은 TTS 의존성·권한·호출이 없다. 내비 UI의 음소거를 켜고 시험한 뒤 원래대로 돌렸다. 리스너는 앱이 백그라운드여도 유지됐으며 요청·콜백에 단조 시계 ms를 남겼다. UI 클릭 표시는 직전 `adb shell log -t T23` 시각이라 ADB 전달 오차가 포함된 단일 측정값이다. 마이크가 없어 Gleo는 시험하지 않았다.

| 설정 경로 | 관측값 | 제한 |
|---|---|---|
| SDK `requestRoute` → 판교역 | 요청 `12:43:33.026` → `onRouteStarted` `12:43:38.873`: **5,847ms**. 이어 `ROUTE_DRIVE` | 기존 경로 교체 중 `ROUTE_CANCELLED/FREE_DRIVE/빈 목적지`가 잠시 옴 |
| 내비 검색 `Pangyo` → `RARADEPANGYO` → 목적지로 | 클릭 표시 `12:48:46.774` → `onRouteStarted` `12:48:52.753`: **5,979ms**, `ROUTE_DRIVE` 10ms 뒤 | 상세 장소를 보는 순간과 경로가 정해지는 순간은 다름. 내비의 경로 계산·안내 시작 대기가 포함됨 |
| 즐겨찾기 → 경기도판교테크노밸리 | 클릭 표시 `12:45:07.092` → `onRouteStarted` `12:45:13.053`: **5,961ms**, 같은 시각 `ROUTE_DRIVE` | 앞서 쓴 같은 목적지를 다시 고른 첫 시험은 콜백까지 60.543초였다. 지연 원인은 미확인이고 항상 6초 이내라고 보장하지 않음 |

새 목적지의 이름은 `onRouteStarted`에서 알 수 있다. **세 경로 모두 이번 관측에서 `onDestinationChanged`는 오지 않았다.** 좌표·주소·남은 거리/시간은 `getDestinationInfo()`를 별도로 불렀을 때 `onDestinationInfo`로 받았다.

- 판교역 요청 좌표 `37.394776/127.111149`는 앞선 첫 시험의 상세 콜백 좌표와 일치했다. 재시험 검색 장소는 `37.39335/127.09847222`, 이름 RARADEPANGYO, 주소 분당구 판교동, 남은 거리 3,500m·시간 720초였다.
- 즐겨찾기 목적지는 `37.40048888/127.10387777`, 이름 경기도판교테크노밸리, 주소 분당구 삼평동, 남은 거리 2,300m·시간 540초였다.
- 즐겨찾기 경로 시작 후 **54.485초** 동안 상세 자동 콜백은 0건이었다. 명시적 조회 뒤 **1,026ms**에 상세가 왔다. 그 뒤 다시 88.822초 동안 상세 자동 콜백이 없었다.
- 3회 폴링 요청은 상세 응답까지 **1,011 / 1,010 / 1,012ms**, 응답 간격 **2,348 / 2,091ms**였다. 이는 앱이 지정한 조회 간격이며 SDK의 고정 push 주기가 아니다.
- `cancelRoute` 마지막 시험: 요청 후 **257ms**에 `onRouteCancelled`, **258ms**에 `FREE_DRIVE`, **297ms**에 빈 목적지. 재조회에서도 `SAFE_GUIDING`·좌표 0/0·빈 이름·거리/시간 0을 확인했다.
- `onRouteEnded`가 경로 시작과 거의 같이 왔고 `RouteStateInfo.isRouting=false`는 ROUTE_GUIDING에서도 계속 false였다. 이 AVD에서 이 둘을 ‘목적지 도착/안내 종료’의 단독 근거로 쓰면 안 된다.

근거 원본: [즐겨찾기·SDK·폴링](parking-travel/navi-02-favorite-and-polls.txt), [검색](parking-travel/navi-03-search.txt), [최종 취소·빈 목적지](parking-travel/navi-04-restoration.txt), [내비 화면](parking-travel/search-route.png). GPS·차량 위치가 고정된 정차 측정이므로 **실제 이동 중 자동 상세 갱신 주기와 남은 거리 감소는 미확인**이다.

권고는 `onRouteStarted` 또는 `NavigationStatus` 변경에서 목적지를 즉시 조회하고 유효 좌표·식별자로 중복을 제거하는 것이다. 남은 거리/시간은 명시적 폴링이 필요하다. 이 측정에서 목적지 선택부터 상세 확보까지의 기대치는 경로 약 6초 + 조회 약 1초이나, 이는 별도 측정값을 더한 추정이며 보장 SLA가 아니다. 같은 목적지 재설정 지연 사례도 있으므로 ‘목적지 선택 즉시’라는 문구·재조회 간격은 Claude가 판단해야 한다.

## 7. 설계 권고와 남은 판단

1. **주차 검색은 후보 1의 ‘검증된 필수 필드만 가진 정적 자산’을 우선 권고**한다. 전체 원본 JSON 약 684MB를 그대로 넣지 않고 수집한 이름·좌표의 최소 gzip 약 7MB를 출발점으로 삼는다. 이름·좌표가 유효한 시설을 ID로 중복 제거하고, 실제 숫자 요금과 지역코드를 오프라인에서 붙인다. 실시간은 ID 단건 조회가 되지 않으므로 자산에 저장한 시도/시군구별 목록을 한 번 받아 ID로 결합해야 한다. 후보 2만 쓰면 목적지 좌표→시군구 코드를 구할 근거가 없고, 지역 경계에서는 인접 지역 누락도 생긴다. 실시간과 이름·좌표까지 연결된 범위는 전국 487개뿐이므로 제공 범위를 명시해야 한다. 요금 포함 최종 APK 크기·전국 요금 다운로드는 후속 자산 제작에서 실측해야 한다.
2. **500m는 유지할 수 있다.** 시청에서 실제 빈자리 후보 2곳을 확보했다. 다만 실시간 지원이 중구 42/3,609, 강남 28/17,084, 울산 남구 0이므로 빈자리 안내의 전국 보편성을 주장하지 않는다. 후보 없음과 API 실패를 구별한다.
3. **10분 신선도는 현재 자료로 판정 불가.** 공급자의 생산시각이나 신선도 보장 없이는 수신시각으로 통과시키지 않는다. 설계를 유지하면 실시간 빈자리 발화는 보류하고 검증된 요금만 사용할 수 있다. 최종 완화·별도 데이터 선택은 Claude에게 요청한다.
4. **행사 5km·명소 3km는 두 표본에서 사용 가능.** 시청은 오늘 행사 14개·명소 66개, 태화강 주변은 오늘 행사 0개·명소 10개였다. 한 번에 전 종류 5km 목록을 받고 명소 종류·3km를 필터링하면 행사 날짜 조회와 합쳐 2회에 들어갈 수 있다. 한 페이지 초과·시도 경계·필드 결측은 따로 처리해야 한다.
5. **여행 트리거는 경로 확정 이벤트 + 목적지 조회로 설계 검토.** `onDestinationChanged`나 상세의 자동 반복만 기다리면 이 AVD에서 놓친다. 목적지 좌표가 바뀌는 것과 일시적인 빈 목적지를 구분하고, 새 경로가 확정되기 전에 과거 목적지의 안내를 내지 않는다.

## 8. 실시간 값 변화

2026-10-29 추가 측정. 기존 `probe_api.py`로 **전국 `PrkRealtimeInfo_v1`, `pageNo=1`, `numOfRows=5000`, `format=2`만 정확히 3회** 호출했다. 요청 시작 시각은 한국시간 **13:11:10.734787 / 13:16:10.747695 / 13:21:10.735781**, 간격은 **300.012908초 / 299.988086초**다. 매번 HTTP 200·결과 코드 0·총계/실제/고유 ID **4,632개**였고 세 응답의 ID 집합도 같았다. 이번 작업에서 다른 API와 에뮬레이터는 사용하지 않았다.

`prk_center_id`가 같은 행의 `pkfc_Available_ParkingLots_total`을 정수로 비교했다. 전체 변화율의 분모는 구간 양끝에서 비교 가능한 공통 ID **4,632개**다. 별도 집합은 최초 T-23의 전국 시설 18페이지와 당시 실시간 목록을 결합해 재구성한 **이름·유효 좌표가 있는 기존 487개**이며, 세 응답 모두 487개가 있어 누락은 없었다.

| 구간 | 전체 변화 ID / 비교 ID | 전체 변화율 | 기존 487개 중 변화 ID / 비교 ID | 집합 내 변화율 |
|---|---:|---:|---:|---:|
| 1→2 (약 5분) | 326 / 4,632 | 7.04% | 1 / 487 | 0.21% |
| 2→3 (약 5분) | 315 / 4,632 | 6.80% | 0 / 487 | 0.00% |
| 1→3 (약 10분) | 411 / 4,632 | 8.87% | 1 / 487 | 0.21% |

장면 D **동국제강 `04540-11291-00001-00-1`의 빈자리는 8 → 8 → 8면**으로 세 번 모두 같았다. 구간별 변화는 양끝의 값이 다른 ID 수이며, 중간에 바뀌었다 원래 값으로 돌아오면 1→3 변화에는 포함하지 않는다.

이 관측은 일부 빈자리 값이 실제로 변한다는 근거다. **값이 그대로라는 사실은 미갱신의 증거가 아니며, 값 변화도 생산시각·절대 나이·10분 신선도를 보장하지 않는다.** 생산/갱신시각 필드는 여전히 없다. 따라서 이 추가 실측만으로 7절의 신선도 미확인을 해소하지 않는다.

근거는 [세 시점 전체 ID의 빈자리 값과 고정 집합 ID](parking-travel/realtime-variation-values.json), [1차](parking-travel/samples/parking-realtime-variation-1.json)·[2차](parking-travel/samples/parking-realtime-variation-2.json)·[3차](parking-travel/samples/parking-realtime-variation-3.json) 요청/응답 발췌, [summary.json의 `realtimeVariation`](parking-travel/summary.json)이다. 발췌는 첫 100행이고 변화율은 별도 근거 파일의 **전체 4,632개 ID**로 계산했다. 키를 제거한 원본과 발췌 해시도 대조했다. 주차 로컬 호출 카운터는 **43→46**, 관광은 **28 유지**다. 아래 명령은 저장된 근거만 읽고 API를 호출하지 않는다.

```powershell

```

두 명령으로 변화·복귀·누락·분모 0 사례를 확인하고 세 구간 결과를 재계산했다. 기존 `analyze.py`로 초기 실측 집계를 다시 만든 경우에는 이 추가 명령도 이어 실행해 `realtimeVariation`을 복원한다. 제품 코드·설계·기존 표본은 수정하지 않았고 push하지 않았다.

## 재현·검증

Windows Python 3.12(`py -3.12`)와 기존 JDK 17/Android SDK를 썼다. 기본 `python`은 실행 별칭만 있어 실패했고 실제 설치된 `py -3.12`로 실행했다. 새 패키지는 설치하지 않았다.

```powershell
py -3.12 spikes/parking-travel/probe_api.py --self-test
py -3.12 spikes/parking-travel/measure.py parking
py -3.12 spikes/parking-travel/measure.py tour
py -3.12 spikes/parking-travel/measure.py national
py -3.12 spikes/parking-travel/analyze.py
py -3.12 spikes/parking-travel/verify.py
cd spikes/parking-travel
.\gradlew.bat :app:assembleDebug --console=plain
```

`measure.py`는 기존 표본을 재사용한다. 대용량 발췌의 전체 원본이 없으면 집계를 거부하므로, 새 PC에서 커밋 표본만으로 전국 통계를 다시 계산했다고 표시할 수 없다. 재실측은 별도 라벨의 `probe_api.py --service ... --operation ... --label ... --param 이름=값`으로 저장하며 키를 인자에 넣지 않는다. 관광 호출수는 로컬 날짜별 파일에 먼저 기록하고 50회부터 거부한다. 표본 실패도 사용량에 포함한다.

별도 앱 빌드·설치·NaviHelper 연결과 콜백 수신을 확인했다. SDK에는 없는 `NaviHelper.isRouting()`을 처음 사용해 빌드가 한 번 실패했고, `getRouteStateInfo`의 실제 응답을 기록하도록 바로잡은 뒤 빌드 성공했다. 소리 나는 TTS·Gleo·실차·주행 GPS 시험은 하지 않았다. 종료 시 경로 취소·빈 목적지·시험 앱 force-stop을 확인했고 시험 즐겨찾기를 삭제했다. 내비 음소거를 복원한 뒤 에뮬레이터 사용 종료를 coordinator에게 알렸다. push하지 않았다.

최종 검증은 별도 Gradle **33개 작업 실행·BUILD SUCCESSFUL**, `verify.py`의 응답 발췌 해시·장면 D/E의 ID/거리/날짜·키 미노출·관광 호출수 상한·타임라인 지연 수치 검사를 통과했다. 제품 앱·core는 다른 작업자가 구현 중이어서 이번 작업에서 빌드하거나 수정하지 않았다.
